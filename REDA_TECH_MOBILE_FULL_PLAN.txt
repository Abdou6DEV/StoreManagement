===============================================================
Corrected against the live desktop app (v6.1.1) and the live LICENSING

PURPOSE
-------
Add a mobile web/PWA in the same StoreManagement repository without breaking
the existing Electron desktop app.

V1 mobile is READ-ONLY.

Build identity, tenant, cloud mirror, sync metadata, and API boundaries so
two-way POS writes can be added later without replacing the foundation.

DO NOT implement two-way mobile writes in V1.


DECISIONS THAT ARE LOCKED
-------------------------
- TWO Supabase projects in TWO organizations:
  1) LICENSING project (existing, fayqqjnhqggmtcwaymwh): licensing, trial,
     customers, device authorization, AI, backups. Stays the source of truth
     for who is a paying customer. The PWA never talks to it.
  2) MOBILE project (NEW, its own organization): everything the PWA touches:
     pos_* mirror, mobile devices, pairing tokens, mobile login. Its Free
     quotas (Edge, egress, storage, 500 MB DB) are separate from licensing.
  customer_id (uuid from licensing) is the tenant key in both.
  Stay on Free for now.
- Pairing authorizes the PHONE. Login authorizes the USER. A shop has multiple
  local users besides admin.
- Persist pairing (device credential). Do NOT persist the user session. Every
  app open requires username/password again.
- Phone login is the same as desktop: username + password. A Supabase Edge
  Function checks the credentials against the synced account; do not require
  email or migrate staff to Supabase Auth for V1.
- QR UX is not important. One pairing token is enough, however it is entered.
- V1 does not clone every desktop module. Sync only what the first read-only
  screens need, plus users so login works.

2. FINAL HIGH-LEVEL ARCHITECTURE
--------------------------------

TWO Supabase projects, each in its own organization.
One shared database per project for ALL shops (tenant column customer_id).
Do NOT create one database per customer.

A) LICENSING project (existing, fayqqjnhqggmtcwaymwh) - mostly unchanged
   - customers, allowed_devices, desktop licensing, trial
   - PC device authorization, device linking
   - AI entitlement/quota
   - existing cloud backup files
   - mobile entitlement per customer: mobile_enabled, mobile_device_limit
     (customer_mobile_settings), returned by device-check
   It stays the single truth for "is this shop licensed / allowed mobile".

B) MOBILE project (new, separate organization)
   - mobile_devices (which phones belong to which customer_id)
   - mobile_pairing_tokens
   - pos_* mirror: products, categories, clients, sales, payments, repairs
   - synced users + permissions (hashes never leave the server / Edge)
   - dashboard aggregates, sync metadata
   - mobile Edge Functions (section 10)
   The PWA talks ONLY to the mobile project.

WHY TWO PROJECTS
- Mobile traffic (sync + PWA reads) cannot use up licensing quotas or
  pause/lock-out licensing, which every desktop depends on.
- Free quotas are per organization, so the mobile org gets its own
  Edge/egress/storage budget and its own 500 MB database.
- The PWA's keys and tokens live in a project that holds no licenses,
  backups, or AI data.

COSTS AND RISKS OF TWO PROJECTS
- The two projects do not share users or database access. Any
  cross-check goes through Edge Functions (see IDENTITY FLOW).
- Each Free project can pause after ~7 days of inactivity and each has its
  own limits. Keep the V1 mirror small (aggregates + recent rows).
- A Free organization allows a limited number of active projects; confirm
  the new org's limits when creating it.
- Two sets of keys/secrets to manage; never mix them up in .env files.

IDENTITY FLOW (two projects)
1. Desktop keeps talking to the LICENSING project with x-app-secret
   (unchanged) for device-check, backups, AI.
2. Desktop talks to the MOBILE project for pairing/sync with its own,
   separate mobile secret/credential. Never put either secret in the PWA.
3. Licensing truth reaches the mobile project server-to-server only:
   mobile Edge Functions verify the desktop's license by calling the
   licensing device-check (or a dedicated licensing function) using a
   secret stored ONLY in the mobile project's Edge Function secrets. The
   desktop and PWA never relay license claims. Fail closed if licensing is
   unreachable (cache a short-lived positive result to limit calls).
4. PWA pairing-complete has no desktop secret; the function validates the
   one-time token and records mobile_devices in the mobile project.
5. PWA login is an Edge Function on the MOBILE project. It checks the
   existing desktop-style username/password against the synced bcrypt hash.
6. The browser never chooses customer_id. The server binds the resulting
   session to the verified user, customer, and paired phone.
7. SESSION METHOD (DECIDED): opaque server-side session ("Option B").
   - mobile-login creates a random, unguessable session code (at least 32
     bytes from a secure random source) and returns it once. No JWT.
   - Only a HASH of the code is stored in a mobile_sessions table with:
     customer_id, mobile_device_id, user_id, created_at, expires_at,
     last_used_at, revoked_at.
   - The PWA keeps the code in memory only (not localStorage), sends it on
     every request, and loses it on close/reload, so login is required again.
   - The PWA NEVER queries pos_* tables directly. All reads go through
     mobile-* read Edge Functions. RLS stays on with no policies for
     anon/authenticated, so the Data API cannot read those tables.
   - On EVERY read, the function: hashes the code, finds the session, checks
     not expired/revoked, checks the phone is active and not revoked, the
     user is active, mobile_enabled and license are still valid (short cache
     allowed), then loads the user's CURRENT permissions and filters data by
     the session's customer_id. Never trust customer_id or permissions sent
     by the browser.
   - Short lifetime (e.g. 30-60 min idle/absolute cap), logout revokes it,
     and revoking a phone or deactivating/changing a user kills their
     sessions immediately.
   - Rate-limit mobile-login per username + phone + IP and lock out after
     repeated failures. Use constant-time-style, generic error messages.
   - Trade-off accepted: more Edge Function calls than direct reads, so keep
     responses small and use pagination/aggregates.
   - Revisit signed JWT + RLS only if usage outgrows this approach.

FREE-TIER PAUSE
Each Free project can pause after ~7 days of inactivity.
Desktops hit the licensing device-check, which keeps THAT project awake,
but NOT the mobile project. Sync and PWA use keep the mobile project awake;
if a shop is idle for a week the phone may fail until unpaused. Show a
clear error, and consider a lightweight scheduled ping or Pro later.


3. CUSTOMER ID VS DEVICE ID
----------------------------

customer_id (uuid):
- identifies the store/business
- is the tenant key on every mobile business row
- is already returned by device-check today

device_id:
- one physical authorized device
- desktop keeps the machine GUID
- each phone gets its own mobile device_id at pairing
- used for revoke, limits, audit
- must NOT identify the shop's data

Example:
Customer <uuid>
  Desktop A -> existing allowed_devices.device_id
  Phone A   -> mobile_devices.device_id
  Phone B   -> mobile_devices.device_id

Revoking Phone B drops that phone only. Shop data stays. Other devices stay.

5. PAIRING, THEN LOGIN EVERY TIME
---------------------------------

Pairing = this phone is allowed for this customer_id.
Login = which SQLite user is using it (permissions).

PAIRING (once per phone, until revoked or storage cleared)
1. Admin enables mobile for that customer.
2. Desktop, already licensed, has customer_id from device-check.
3. Desktop creates a short-lived one-time pairing token.
4. Phone opens the PWA and submits that token (paste, QR, whatever).
5. Backend validates token, license, mobile_enabled, device limit.
6. Backend registers mobile_devices and returns a device credential.
7. PWA stores only the DEVICE pairing credential.
8. Desktop starts (or continues) cloud sync for that customer_id,
   USERS FIRST.

LOGIN (every time the PWA is opened)
1. PWA checks stored device pairing (mobile-device-check).
   Revoked / disabled / expired license → clear pairing, show pair again.
2. If pairing is valid, show username/password. Never skip this.
3. PWA sends credentials over HTTPS to mobile-login.
4. Function verifies bcrypt against the synced user row for that
   customer_id, checks isActive + permissions, checks device still active.
   This is the existing desktop username/password login, not email login and
   not a Supabase Auth account.
5. Function creates an opaque session (see IDENTITY FLOW step 7) bound to
   customer_id, mobile_device_id and user_id, and returns the random code.
   Role and permissions are NOT baked into the code; they are loaded from
   the synced rows on every request.
6. Closing the app / next visit: pairing remains, user token does NOT.
   Password again.

MUST NOT:
- persist user login in localStorage as authorization
- expose bcrypt hashes to the browser
- send SQLite or x-app-secret to the phone
- let the browser pick customer_id
- use desktop activation-key login on mobile
- show a working login screen before users for that tenant have synced

SYNC ORDER (the bug the original plan got wrong)
Pairing may complete first.
Login MUST wait until User + UserPermissions for that customer_id exist
in the pos_* tables. Desktop should upload users immediately when
mobile is enabled / pairing is created, before other entities if needed.
Password changes on desktop must sync before that user can log in on
the phone.

8. SYNC ARCHITECTURE
--------------------

V1:

Desktop SQLite  --incremental outbox-->  MOBILE Supabase (pos_*)  --read-->  PWA

SQLite remains operational source of truth.
Mobile DB is a mirror.
PWA is read-only.

Desktop SyncOutbox:
- entity_type, entity_id, operation (CREATE/UPDATE/DELETE)
- changed_at, sync_version, retry_count, last_error, synced_at

Local transaction ALWAYS commits first. Sync is secondary.
Never roll back a local sale because cloud is down.
Batch/debounce. Background. Show last sync time / errors in desktop settings.
Initial sync is resumable and must not freeze the POS UI.

USERS AND PERMISSIONS ARE FIRST-CLASS OUTBOX ENTITIES.

When mobile is enabled, enqueue users immediately, then catalogue data,
then recent sales/payments/repairs, then backfill.

Desktop talks to the MOBILE project with NEW, separate settings (e.g.
STORE_MOBILE_SUPABASE_URL / _ANON_KEY / _APP_SECRET), only from the Electron
main process, via mobile-sync-ingest. Do not reuse STORE_ONLINE_* values and
never put any desktop secret in the PWA. As with the licensing secret, treat a
secret shipped with the desktop app as extractable: the mobile project must
also validate the desktop device/license server-side (see IDENTITY FLOW).
Idempotent upserts on (customer_id, source_id, sync_version).

PWA V1 refresh: pull-to-refresh / open fetch. Realtime is not required.
Cache last successful read; label it stale when offline.
Do not implement mobile write outbox in V1, but keep IDs/tenants clean
so it can be added.

Backup restore on desktop rewrites SQLite. That must trigger a full
resync (or wipe+replace that tenant's mirror). Otherwise the phone lies.

Conflict resolution is NOT in V1. Future writes need operation_id
idempotency. Sales should stay events; stock should become movements
rather than last-write-wins quantity. Do not implement that now.


9. SECURITY
-----------

PWA
 -> mobile project publishable key + device credential + session code
 -> mobile-* Edge Functions (validate session, filter by customer_id,
    enforce permissions)
 -> Postgres (service role used inside functions only)

Never in the PWA:
- service-role
- STORE_ONLINE_APP_SECRET / x-app-secret (licensing)
- the mobile desktop secret, or any licensing-project key
- password hashes

Database tables (pos_*, mobile_*): RLS enabled, NO policies for
anon/authenticated, so the Data API cannot read them directly. Access is
only through the Edge Functions above, which must always filter by the
session's server-side customer_id and check the user's current permissions.

pos_users.password_hash is never returned by any function.

Tenant tests before production:
- shop A cannot read shop B
- revoked phone cannot read
- mobile_enabled false cannot read
- expired license cannot pair; existing sessions fail check
- limit reached cannot pair
- expired/used pairing token rejected

15. IMPLEMENTATION RULES
------------------------

1. Do not rewrite the desktop database. SQLite stays.
2. Keep licensing and mobile in separate Supabase projects/organizations.
   Put pos_* tables and mobile devices only on the mobile project; the PWA
   never contacts the licensing project. Isolate shops with tenant checks
   and tenant checks inside the mobile Edge Functions (RLS is on with no policies).
3. Do not put mobile code inside src/ or import it into Electron.
4. Do not expose service-role or x-app-secret to the PWA.
5. customer_id (uuid) is the tenant. device_id is not.
6. Do not copy the SQLite backup into the mobile DB.
7. No two-way writes in V1.
8. Persist device pairing only. Login every time.
9. Users/permissions must sync before login can succeed.
10. Browser never chooses customer_id.
11. Local desktop commits do not depend on cloud success.
12. Keep desktop UUIDs; categories use name as source_id.
13. Sync is async/batched/idempotent.
14. Backup restore ⇒ full tenant resync.
15. Test desktop login, licensing, backup, AI, and npm run make
    after every phase.
