DECISIONS THAT ARE LOCKED
-------------------------
- ONE Supabase project (the existing one). Free Edge/egress/storage/MAU quotas
  are per ORGANIZATION, summed across projects. A second project does not
  double those limits and only adds JWT glue. Stay on Free; paying is not
  required yet. Keep POS mirror in a `pos_*` schema/tables on the same DB.
- Pairing authorizes the PHONE. Login authorizes the USER. A shop has multiple
  local users besides admin.
- Persist pairing (device credential). Do NOT persist the user session. Every
  app open requires username/password again.
- Phone login is the same as desktop: username + password. A Supabase Edge
  Function checks the credentials against the synced account; do not require
  email or migrate staff to Supabase Auth for V1.
- QR UX is not important. One pairing token is enough, however it is entered.
- V1 does not clone every desktop module. Sync only what the first read-only
  screens need, plus users so login works.

2. FINAL HIGH-LEVEL ARCHITECTURE
--------------------------------

ONE Supabase project. One shared database for all shops.
Do NOT create one database per customer.
Do NOT create a second project to "split Free quota".

Same project, two concerns (tables stay separate):

A) CONTROL (already exists)
   - customers, allowed_devices, desktop licensing, trial

B) POS MIRROR (new tables on this same project, pos_* prefix)

WHY NOT TWO PROJECTS
Supabase Free is organization-based billing. Quotas are summed across
every project in the org:

- Edge Function invocations: 500,000 / month for the WHOLE org
- Egress: 5 GB for the WHOLE org
- File storage: 1 GB for the WHOLE org
- Auth MAU / Realtime: org-wide
- Database size: 500 MB PER PROJECT (the only per-project exception)

A second project does NOT give extra Edge invocations. Licensing + mobile
sync + login would still share the same 500k. It would add:
- a second 500 MB disk
- a second idle-pause risk
- JWT that cannot cross projects

Current DB is ~13 MB. Keep V1 mirror small (aggregates + recent rows).
If this one 500 MB disk fills later, then consider a second project or Pro.
Do not pay yet.

IDENTITY FLOW (one project, no JWT bridge)
1. Desktop talks to the existing project with x-app-secret (unchanged).
2. Desktop sync/ingest uses the same secret or a dedicated Edge Function.
   Never put that secret in the PWA.
3. PWA pairing-complete has no x-app-secret; the function validates the
   token and records mobile_devices.
4. PWA login is an Edge Function on this same project. It checks the existing
   desktop-style username/password against the synced bcrypt hash.
5. The browser never chooses customer_id. The server binds the resulting
   session to the verified user, customer, and paired phone.
6. Before implementation, define how the session is authenticated for reads:
   either a Supabase-trusted signed JWT for RLS, or an opaque session
   credential that every read Edge Function validates. Do not assume that an
   arbitrary token returned by an Edge Function is accepted by Supabase RLS.

FREE-TIER PAUSE
A Free project can pause after ~7 days of inactivity.
Desktops already hit device-check; that keeps this project awake.
If every shop is offline for a week, unpause in the dashboard.


3. CUSTOMER ID VS DEVICE ID
----------------------------

customer_id (uuid):
- identifies the store/business
- is the tenant key on every mobile business row
- is already returned by device-check today

device_id:
- one physical authorized device
- desktop keeps the machine GUID
- each phone gets its own mobile device_id at pairing
- used for revoke, limits, audit
- must NOT identify the shop's data

Example:
Customer <uuid>
  Desktop A -> existing allowed_devices.device_id
  Phone A   -> mobile_devices.device_id
  Phone B   -> mobile_devices.device_id

Revoking Phone B drops that phone only. Shop data stays. Other devices stay.

5. PAIRING, THEN LOGIN EVERY TIME
---------------------------------

Pairing = this phone is allowed for this customer_id.
Login = which SQLite user is using it (permissions).

PAIRING (once per phone, until revoked or storage cleared)
1. Admin enables mobile for that customer.
2. Desktop, already licensed, has customer_id from device-check.
3. Desktop creates a short-lived one-time pairing token.
4. Phone opens the PWA and submits that token (paste, QR, whatever).
5. Backend validates token, license, mobile_enabled, device limit.
6. Backend registers mobile_devices and returns a device credential.
7. PWA stores only the DEVICE pairing credential.
8. Desktop starts (or continues) cloud sync for that customer_id,
   USERS FIRST.

LOGIN (every time the PWA is opened)
1. PWA checks stored device pairing (mobile-device-check).
   Revoked / disabled / expired license → clear pairing, show pair again.
2. If pairing is valid, show username/password. Never skip this.
3. PWA sends credentials over HTTPS to mobile-login.
4. Function verifies bcrypt against the synced user row for that
   customer_id, checks isActive + permissions, checks device still active.
   This is the existing desktop username/password login, not email login and
   not a Supabase Auth account.
5. Function returns a short-lived user session credential bound to:
   customer_id, mobile_device_id, user_id, role, permissions.
   Its verification method must be defined as in the identity flow above.
6. Closing the app / next visit: pairing remains, user token does NOT.
   Password again.

MUST NOT:
- persist user login in localStorage as authorization
- expose bcrypt hashes to the browser
- send SQLite or x-app-secret to the phone
- let the browser pick customer_id
- use desktop activation-key login on mobile
- show a working login screen before users for that tenant have synced

SYNC ORDER (the bug the original plan got wrong)
Pairing may complete first.
Login MUST wait until User + UserPermissions for that customer_id exist
in the pos_* tables. Desktop should upload users immediately when
mobile is enabled / pairing is created, before other entities if needed.
Password changes on desktop must sync before that user can log in on
the phone.

8. SYNC ARCHITECTURE
--------------------

V1:

Desktop SQLite  --incremental outbox-->  same Supabase (pos_*)  --read-->  PWA

SQLite remains operational source of truth.
Mobile DB is a mirror.
PWA is read-only.

Desktop SyncOutbox:
- entity_type, entity_id, operation (CREATE/UPDATE/DELETE)
- changed_at, sync_version, retry_count, last_error, synced_at

Local transaction ALWAYS commits first. Sync is secondary.
Never roll back a local sale because cloud is down.
Batch/debounce. Background. Show last sync time / errors in desktop settings.
Initial sync is resumable and must not freeze the POS UI.

USERS AND PERMISSIONS ARE FIRST-CLASS OUTBOX ENTITIES.

When mobile is enabled, enqueue users immediately, then catalogue data,
then recent sales/payments/repairs, then backfill.

Desktop talks to this project with existing STORE_ONLINE_* / x-app-secret
(or a dedicated sync Edge Function). Never put that secret in the PWA.
Idempotent upserts on (customer_id, source_id, sync_version).

PWA V1 refresh: pull-to-refresh / open fetch. Realtime is not required.
Cache last successful read; label it stale when offline.
Do not implement mobile write outbox in V1, but keep IDs/tenants clean
so it can be added.

Backup restore on desktop rewrites SQLite. That must trigger a full
resync (or wipe+replace that tenant's mirror). Otherwise the phone lies.

Conflict resolution is NOT in V1. Future writes need operation_id
idempotency. Sales should stay events; stock should become movements
rather than last-write-wins quantity. Do not implement that now.


9. SECURITY
-----------

PWA
 -> project anon key + user/device tokens
 -> RLS + Edge Functions
 -> Postgres

Never in the PWA:
- service-role
- STORE_ONLINE_APP_SECRET / x-app-secret
- password hashes

RLS on every mobile business table:
- jwt customer_id matches row customer_id
- device still active
- mobile_enabled (checked at login/device-check, not only UI)

Authorize with app_metadata / server-issued claims, never user_metadata.

pos_users.password_hash: revoke SELECT from authenticated/anon.
Only a security-definer Edge path may read it.

Tenant tests before production:
- shop A cannot read shop B
- revoked phone cannot read
- mobile_enabled false cannot read
- expired license cannot pair; existing sessions fail check
- limit reached cannot pair
- expired/used pairing token rejected
