Store Management – Online Features Plan (Working Draft)
Last updated: 2026-05-12 (checkpoint: nav trial/paid-expiry banners; License tab manual online check + shared license state; cloud backup upload IPC + Backup tab button; login cloud restore + download version gate still open)

Goal
- Add lightweight “online” capabilities (not fully cloud): device activation / deactivation, optional time-limited activation, and online backup upload.
- App remains primarily local/offline (local Prisma/SQLite DB).

High-level UX + routing rule (RECOMMENDED DEFAULT / professional)
- The app has three “zones”:
  1) **Pre-login zone** (always accessible): Login, Admin recovery login, Restore-from-online (only on fresh/empty DB + online).
  2) **Main app zone** (protected): requires successful login AND valid license (or valid offline grace).
  3) **License waiting zone**: shown when device is not licensed; collects device/customer info and polls until activated.
- Never hard-block the entire app at boot. Only block access to the **Main app zone** when unlicensed.

What we agreed on (so far)

1) Device identity (per-device licensing)
- Use the existing Windows MachineGuid already used in the app today.
  - Source: system API -> main reads registry key:
    HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid
- The client will send you this GUID, and you will allowlist it server-side.

2) Licensing model (no license keys)
- No end-user license key entry required.
- Supabase stores provisioning + licensing in **`allowed_devices`** (and related **`customers`**). The app asks Edge Function **`device-check`** whether this device may run.
- You (admin) control **paid** activation/deactivation in Supabase (`active`, `expires_at`). During the **free trial**, the device can be allowed **without** setting `active = true` (see **2.1**).
  - If **`device-check`** returns not allowed, the user is redirected to a license/activation waiting page (see section 9).

2.1) Seven-day free trial — new PC (AGREED)
- **Goal:** Any **new** device that completes registration (`device-request`) gets **7 calendar days** of access **before** you decide paid activation. No manual Supabase row for the happy path.
- **Data model:** column **`allowed_devices.trial_ends_at`** (`timestamptz`, nullable).
  - **First provision** (first time this `device_id` gets an `allowed_devices` row): set
    - `trial_ends_at = now() + 7 days` (UTC),
    - `active = false`,
    - `expires_at = NULL` (paid expiry is separate from trial end).
  - Optional later: `trial_started_at` for support only (not required for logic).
- **`device-check` allow rule** (single source of truth — implement identically everywhere, including **backup** Edge Functions unless you explicitly want to block backups during trial):
  - **`allowed: true`** if **either**:
    1. **Trial still valid:** `trial_ends_at IS NOT NULL AND trial_ends_at > now()` (UTC), **or**
    2. **Paid / granted:** `active = true AND (expires_at IS NULL OR expires_at > now())`.
  - **`allowed: false`** if no row, trial ended and (2) is false, or paid subscription expired.
- **After trial:** user is blocked until you set **`active = true`** (and **`expires_at`** if limited paid). You may set **`trial_ends_at = NULL`** when activating paid (optional clarity).
- **`device-request` idempotency:** if `allowed_devices` **already exists** for `device_id`, **do not** extend or restart **`trial_ends_at`** on repeat calls (only set trial on **first insert**). You may still update `customer_id` / inbox rows.
- **Repository:** SQL migration + reference Edge Functions live under **`supabase/`** in this repo (deploy to your Supabase project).

3) Paid activation: lifetime vs limited-time (after trial or direct grant)
- Applies when the device is on **paid** access (section **2.1** trial no longer covers them, or you skipped trial manually).
- Use a nullable **`expires_at`** on **`allowed_devices`** when **`active = true`**.
  - Lifetime paid: `active=true` and `expires_at = NULL`
  - Limited-time paid: `active=true` and `expires_at` in the future
- **Paid allow rule** (subset of **2.1** rule (2)):
  - `active == true AND (expires_at IS NULL OR expires_at > now())`

4) Security approach
- Do NOT embed Supabase service role key in the app.
- Use a secure backend endpoint (Supabase Edge Function recommended) that the app calls to check whether a device is allowed.
- Protect the Edge Function with a simple shared secret header (e.g. `x-app-secret`).
 - (RECOMMENDED DEFAULT): use the same `x-app-secret` protection for backup endpoints too (upload/list/download).
 - (RECOMMENDED DEFAULT): keep Supabase Edge Functions “Verify JWT” enabled and send `Authorization: Bearer <anon key>` in addition to `x-app-secret`.

5) Offline behavior (agreed)
- Licensing is checked when entering the **Main app zone** (after successful login / before protected routes):
  - If internet is available, app verifies with **`device-check`** (valid **trial** or **paid** per section **2.1** / **3**).
  - If internet is NOT available, app can still enter the main app only if the offline grace window has NOT expired.
- If offline grace window is expired, the app must force an online check (require internet) before allowing entry to the main app.
- Offline grace period: 7 days.
- Grace reset rule:
  - On a successful online login where the device is confirmed licensed, reset the grace timer.
  - When the app becomes offline, start counting the 7-day grace window from the last successful online license check.
- Grace storage (agreed):
  - Persist license check timestamps/state in the local SQLite DB (Option table) via existing `options.get/set`, not browser localStorage.
- Never successfully verified online: if the device has **never** received **`allowed: true`** from **`device-check`** (no row yet, or not provisioned), offline behavior matches “not licensed”:
  - The app must be online to register and verify.
- **During a valid trial or paid license**, the same offline grace rules apply as for any other allowed device (7 days from last successful online check that returned allowed).
- **Grace vs server trial / paid end (AGREED — implement in app):** Offline grace and server dates are **two different clocks**. Grace alone must **not** let the main app run **past** a trial or paid end time that the app **already learned** from the last successful **`device-check`**.
  - On each successful online check with **`allowed: true`**, persist the server timestamps returned in that response (**`trial_ends_at`**, **`expires_at`**) alongside **`license.last_ok_at_ms`** / **`license.last_ok_grace_until_ms`** (see section **14**).
  - Compute **`grace_until`** = **`last_ok_at + 7 days`** (same as today).
  - **Effective offline deadline** for main-app access = the **earliest** of:
    - **`grace_until`**, and
    - **`trial_ends_at`** (if not null on that response — caps trial / trial-still-valid path), and
    - **`expires_at`** (if not null on that response — caps limited paid).
  - Missing **`trial_ends_at`** or **`expires_at`** means **no cap** from that field (e.g. lifetime paid has no **`expires_at`** → only grace applies). If both caps exist, **`min(...)`** still applies (conservative).
  - **Rationale:** avoids a long offline window where **`grace_until`** alone would extend access **after** the server would already return **`allowed: false`** for expired trial or subscription.

6) Online backups (direction)
- Current app already creates local DB backups under userData/backups.
- Plan: upload backup DB files (or the newest daily backup) to cloud storage and keep metadata in DB.
- Details (bucket/table, upload mechanism) still to be decided.
- Auto-upload behavior (future, optional):
  - Auto-upload may be added later as an optional feature (user can enable/disable it in settings).
 - v1 upload behavior (RECOMMENDED DEFAULT):
   - Manual upload only (from the backup page). No automatic uploads in v1.
   - Auto-upload may be added later as an optional setting, but not required for initial release.
- Non-goal (AGREED):
  - No row-by-row / realtime database sync. Online data movement is backup upload/download only.
 - Cloud retention + overwrite policy (AGREED):
   - Keep only 1 cloud backup per customer (always the latest).
   - Manual “Upload now” from the backup page:
     - create a new local backup first
     - upload it
     - delete/overwrite the previous cloud backup for that customer
   - Automatic uploads (if enabled later) should follow the same “latest only” rule.
 - Cloud storage layout (RECOMMENDED DEFAULT):
   - Store at a fixed path (overwrite each time):
     - `backups/<customer_id>/latest.db`
     - `backups/<customer_id>/latest.json` (metadata)
 - Metadata to store (RECOMMENDED DEFAULT):
   - `uploaded_at` (ISO timestamp)
   - `size_bytes`
   - `source` (e.g. `manual_upload` / `auto_upload`)
   - `app_version` (REQUIRED) — used for restore compatibility checks
   - `device_id` (optional, for troubleshooting)
 - Restore compatibility rule (RECOMMENDED DEFAULT, simple):
   - On restore: read `latest.json` first.
   - If `latest.json.app_version` is newer than the installed app version → block restore and require updating the app first.
   - Rationale: avoids restoring a DB created by a newer schema into an older app.
 - Restore behavior (RECOMMENDED DEFAULT):
   - Restore downloads `latest.db` for the provided `customer_id` and replaces the local DB.
   - After restore completes: force logout and redirect to `/login`.
   - Licensing rules still apply normally after restore (if offline grace expired, must go online to log in).

7) Supabase project strategy (multiple apps)
- Use a separate Supabase project per app/product (Store Management app gets its own Supabase project).
- Keep it simple and isolated (data, Edge Functions, activations, backups per app).

7.1) Activation management (agreed)
- **Paid access:** manage **`allowed_devices`** in the Supabase dashboard (`active`, `expires_at`). **`trial_ends_at`** is normally set by **`device-request`** on first provision (section **2.1**); manual edits are for support only.

8) Admin recovery login (keep simple)
- Keep the existing “activation key” login as an ADMIN recovery method (for forgotten credentials).
- This recovery key is separate from online device activation:
  - Even if recovery login succeeds, the app should still require the device to be **allowed** per **`device-check`** (valid **trial** per **2.1** **or** **paid** per section **3**).

9) License/activation waiting page + polling (agreed)
- If login succeeds but the device is not licensed (**`device-check`** not allowed: no row / trial ended and not paid / paid expired / revoked), redirect to a license validation page:
  - **Current UI:** messaging + **pricing** + **sign out**; no MachineGuid block, no “check again” button (product choice for less clutter). **Registration (name + phone)** for brand-new PCs remains on **Welcome** / **`device-request`**, not duplicated as a form on the gate.
  - Remove the input that lets the user enter a validation key (activation is server-side now) — **done** on the gate screen.
  - If offline: show that the device must be online to register or verify — **partially** covered by login-time **`device-check`** errors; gate assumes session already opened after online check returned **not allowed**.
- **Spec (still optional in app):** While online on that page: poll **`device-check`** periodically until **`allowed: true`** (supplier set **paid** `active`, or **trial** still valid after **`device-request`** provisioning).
  - Polling strategy: start fast (e.g. 5–10s for ~1–2 minutes) then back off (30s → 60s → a few minutes) to reduce load.
  - Polling schedule (RECOMMENDED DEFAULT):
    - every 5s for 60s
    - then every 15s for 120s
    - then every 60s until activated (or until user leaves the page)
 - Auto data collection + auto provisioning (AGREED — target behavior):
   - When: device is **not** in `allowed_devices` yet (never provisioned) **or** you treat “first registration” as the name/phone step (exact trigger is app-side; server should be idempotent).
   - License waiting page shows **name + phone**; app calls **`device-request`** with `{ device_id, name, phone }`.
   - Edge Function **`device-request`** must (single place of truth — **admin does NOT manually create `customers` rows** for normal flow):
     1. Normalize `phone` → `phone_normalized`.
     2. If a **`customers`** row exists with matching `phone` (same normalized value stored on `customers.phone`): use that `customer_id`.
     3. Else **INSERT** a new row into **`customers`** (`name`, `phone` = normalized) and use the new `customer_id`.
     4. **Insert or update `allowed_devices`** (idempotent):
        - **First time** this `device_id`: **INSERT** with `customer_id`, **`active = false`**, **`expires_at = NULL`**, **`trial_ends_at = now() + 7 days`**.
        - **Existing row**: **UPDATE** e.g. `customer_id` only; **preserve** existing **`trial_ends_at`** (do **not** reset or extend trial on repeat **`device-request`**).
     5. Update **`device_requests`**: link `customer_id`, keep `status = pending` (or `provisioned`) — inbox only; **paid licensing** after trial is still **`allowed_devices.active`** (+ `expires_at`).
   - **Admin work after trial**: open **`allowed_devices`** and set **`active = true`** (and **`expires_at`** for limited paid). **During the 7-day trial**, no admin click is required for access.
   - **Trial access**: after step 4 first insert, **`device-check`** returns **`allowed: true`** until **`trial_ends_at`** passes (unless you revoke by clearing trial / deleting row — product choice).
 - Note: Deploy **`device-request`** from **`supabase/functions/device-request`** (or equivalent) so it matches **2.1** + the steps above. Older “pending row only” deploys must be upgraded.
 - Duplicate handling / validation (AGREED):
   - Prefer match on **normalized phone**; optional extra check on name if you want fewer false merges.
   - If two shops share one phone, admin fixes linkage in dashboard (edge case).
