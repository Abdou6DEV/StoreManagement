Store Management – Online Features Plan (Working Draft)
Last updated: 2026-05-06

Goal
- Add lightweight “online” capabilities (not fully cloud): device activation / deactivation, optional time-limited activation, and online backup upload.
- App remains primarily local/offline (local Prisma/SQLite DB).

What we agreed on (so far)

1) Device identity (per-device licensing)
- Use the existing Windows MachineGuid already used in the app today.
  - Source: system API -> main reads registry key:
    HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid
- The client will send you this GUID, and you will allowlist it server-side.

2) Licensing model (no license keys)
- No end-user license key entry required.
- Supabase stores an “allowed devices” list; the app is allowed to run if the current device GUID is active (and not expired).
- You (admin) control activation/deactivation in Supabase.
  - If a device is not allowed, user is redirected to a license/activation waiting page (see section 9).

3) Lifetime vs limited-time activation
- Use a nullable expiry timestamp.
  - Lifetime activation: active=true and expires_at = NULL
  - Limited-time activation: active=true and expires_at = now() + N days
- Allow rule:
  - active == true AND (expires_at IS NULL OR expires_at > now())

4) Security approach
- Do NOT embed Supabase service role key in the app.
- Use a secure backend endpoint (Supabase Edge Function recommended) that the app calls to check whether a device is allowed.
- Protect the Edge Function with a simple shared secret header (e.g. `x-app-secret`).
 - (RECOMMENDED DEFAULT): use the same `x-app-secret` protection for backup endpoints too (upload/list/download).

5) Offline behavior (agreed)
- Licensing is checked during login:
  - If internet is available, app verifies device status with Supabase (active + not expired).
  - If internet is NOT available, app can still run only if the offline grace window has NOT expired.
- If offline grace window is expired, the app must force an online check (require internet) before allowing login to proceed.
- Offline grace period: 7 days.
- Grace reset rule:
  - On a successful online login where the device is confirmed licensed, reset the grace timer.
  - When the app becomes offline, start counting the 7-day grace window from the last successful online license check.
- Grace storage (agreed):
  - Persist license check timestamps/state in the local SQLite DB (Option table) via existing `options.get/set`, not browser localStorage.
- Unactivated devices: if the device has never been activated (no prior successful online activation), offline behavior is the same as “not licensed” / deactivated:
  - The app must be online to activate.

6) Online backups (direction)
- Current app already creates local DB backups under userData/backups.
- Plan: upload backup DB files (or the newest daily backup) to cloud storage and keep metadata in DB.
- Details (bucket/table, upload mechanism) still to be decided.
- Auto-upload behavior (future, optional):
  - Auto-upload may be added later as an optional feature (user can enable/disable it in settings).
 - v1 upload behavior (RECOMMENDED DEFAULT):
   - Manual upload only (from the backup page). No automatic uploads in v1.
   - Auto-upload may be added later as an optional setting, but not required for initial release.
- Non-goal (AGREED):
  - No row-by-row / realtime database sync. Online data movement is backup upload/download only.
 - Cloud retention + overwrite policy (AGREED):
   - Keep only 1 cloud backup per customer (always the latest).
   - Manual “Upload now” from the backup page:
     - create a new local backup first
     - upload it
     - delete/overwrite the previous cloud backup for that customer
   - Automatic uploads (if enabled later) should follow the same “latest only” rule.
 - Cloud storage layout (RECOMMENDED DEFAULT):
   - Store at a fixed path (overwrite each time):
     - `backups/<customer_id>/latest.db`
     - `backups/<customer_id>/latest.json` (metadata)
 - Metadata to store (RECOMMENDED DEFAULT):
   - `uploaded_at` (ISO timestamp)
   - `size_bytes`
   - `source` (e.g. `manual_upload` / `auto_upload`)
   - `app_version` (REQUIRED) — used for restore compatibility checks
   - `device_id` (optional, for troubleshooting)
 - Restore compatibility rule (RECOMMENDED DEFAULT, simple):
   - On restore: read `latest.json` first.
   - If `latest.json.app_version` is newer than the installed app version → block restore and require updating the app first.
   - Rationale: avoids restoring a DB created by a newer schema into an older app.
 - Restore behavior (RECOMMENDED DEFAULT):
   - Restore downloads `latest.db` for the provided `customer_id` and replaces the local DB.
   - After restore completes: force logout and redirect to `/login`.
   - Licensing rules still apply normally after restore (if offline grace expired, must go online to log in).

7) Supabase project strategy (multiple apps)
- Use a separate Supabase project per app/product (Store Management app gets its own Supabase project).
- Keep it simple and isolated (data, Edge Functions, activations, backups per app).

7.1) Activation management (agreed)
- Manage device activation/deactivation directly in the Supabase dashboard (manual insert/update of `allowed_devices` rows).

8) Admin recovery login (keep simple)
- Keep the existing “activation key” login as an ADMIN recovery method (for forgotten credentials).
- This recovery key is separate from online device activation:
  - Even if recovery login succeeds, the app should still require the device to be allowed (active + not expired) in Supabase.

9) License/activation waiting page + polling (agreed)
- If login succeeds but the device is not licensed (not found / active=false / expired), redirect to a license validation page:
  - Show the MachineGuid (same as today) and instruct the user to send it to the supplier for activation.
  - Remove the input that lets the user enter a validation key (activation is server-side now).
  - If offline: show that the device must be online to be activated.
- While online on that page: poll Supabase periodically to detect activation, then automatically unlock the app.
  - Polling strategy: start fast (e.g. 5–10s for ~1–2 minutes) then back off (30s → 60s → a few minutes) to reduce load.
  - Polling schedule (RECOMMENDED DEFAULT):
    - every 5s for 60s
    - then every 15s for 120s
    - then every 60s until activated (or until user leaves the page)
 - Auto data collection (AGREED):
   - On first-time / never-activated devices, the license page should include inputs for customer details (e.g. `name`, `phone`).
   - When online, the app submits `{ device_id, name, phone }` to Supabase via an Edge Function to create/update a pending request.
   - This is for admin identification and duplicate prevention; it does NOT automatically license the device.
 - Duplicate handling / validation (AGREED):
   - Normalize phone numbers server-side (remove spaces/dashes, normalize prefix) and prefer matching by normalized phone.
   - If a matching customer already exists (same normalized phone; optionally same name too), link the request to that customer.
   - Otherwise create a new customer record in a pending state (or create a customer request record) for admin review.
   - Admin final step remains: create/update `allowed_devices` with `active/expires_at` to license the device.

Implementation notes (high-level)
- Add new IPC handlers in Electron main to call the Edge Function(s).
- Renderer calls `window.api.*` to check activation during startup/login flow.

Open decisions / next questions
- (Resolved) Offline grace period duration: 7 days.
- Backup upload: which file to upload (daily backup vs live DB) and retention policy.

Unfinished questions / decisions (must answer before implementation)

10) Backups: how to link old backups after PC change
- MachineGuid cannot be entered/changed on a new PC, so backups cannot be keyed only by `device_id` if we want easy restore on a new machine.
- Decide backup ownership identity:
  - Option A (AGREED): introduce a stable `customer_id` (UUID) and store it on `allowed_devices` (foreign key to `customers`). Backups belong to `customer_id` (not `device_id`).
  - Notes:
    - Admin must be able to look up `customer_id` by customer name/phone in Supabase.
    - Customer receives their `customer_id` from admin (treated like a secret).

11) Where can user restore when unlicensed / on a fresh PC
- A new PC may have an empty local DB (no users) until restore.
- Decide where to expose “Restore from online backup”:
  - (AGREED): Login screen only (pre-login). Not only inside the main app.
- Restore availability constraint (AGREED):
  - “Restore from online backup (different PC)” should only be enabled when the local DB is empty / fresh install.
  - If local DB already contains data, hide/disable this option to prevent accidental overwrite (use existing backup/restore tools inside the app instead).
 - Online requirement (RECOMMENDED DEFAULT):
   - Restore-from-online requires internet access. If offline, show a message that restore needs an internet connection.
- Definition of “empty DB” (AGREED):
  - “Empty” ignores default/system tables such as `users` (default admin may exist), `option` (settings), and logs.
  - Consider DB “NOT empty” if ANY of these core modules has data:
    - Stock/Products
    - Cashier/Sales
    - Clients
    - Bills
    - Services

12) Supabase implementation details still pending
- Finalize schema (after deciding `customer_id`):
  - `customers` (include `id`, and fields for admin lookup like `name` and optional `phone`)
  - `allowed_devices` (include `device_id`, `customer_id`, `active`, `expires_at`)
  - `backups` table + Storage bucket layout
- Implement Edge Functions:
  - `device-check` (already chosen: protected by `x-app-secret`)
  - backup list/upload/download endpoints (depend on ownership model)

13) Polling schedule exact values
- (RESOLVED): Polling schedule values defined in section 9.

14) DB Option keys for grace (exact names)
- Decide exact Option keys to store grace/license state, e.g.:
  - `license.last_ok_at`
  - `license.last_ok_expires_at`
  - `license.last_ok_allowed`
 - (RECOMMENDED DEFAULT – lock names for implementation):
   - `license.last_ok_at_ms` (number as string; Date.now())
   - `license.last_ok_grace_until_ms` (number as string; last_ok + 7 days)
   - `license.last_ok_expires_at_ms` (number as string or empty; mirrors server expiry when provided)

15) App routing/licensing refactor scope
- Current `App.tsx` blocks the whole app when `licenseContext` says invalid (old offline activation-key model).
- We must refactor to match the new flow:
  - allow reaching login
  - after login: if not licensed -> redirect to license waiting page and start polling
  - update `licenseValidation.tsx` to remove the “enter activation key” input (this adds/changes UI text → requires translations).

16) Online backup upload mode for large DBs
- Upload method (RECOMMENDED DEFAULT):
  - Simple upload + retry (no resumable/chunked in v1).
